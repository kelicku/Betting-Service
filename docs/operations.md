# 運用・保守説明書

## 日常業務（管理画面）

| 業務 | 画面 | 担当権限 |

| 交換申請の処理：申請受付 → 承認 → 発送準備 → 発送済み（配送業者・追跡番号）→ 完了。不備は却下（理由を入力） | 交換申請管理 | スタッフ |

状態遷移・却下・発送はユーザーに通知とメールで知らされる。

### 会員へのメッセージ送信

メッセージは会員のお知らせ欄（画面右上のベル）に届き、未読件数が表示される。「メールでも送信する」を選ぶと、
メール確認済みの会員にメールも送信する（お試しアカウント・利用停止中の会員を除く）。送信前に対象人数を確認でき、
送信内容は配信履歴と操作履歴に残る。リンク先はサイト内のページのみ指定できる（外部サイトへの誘導による
なりすましを防ぐため）。一斉メールは大量になると送信に時間がかかるため、本番で数万通規模を送る場合は
メール配信サービスの一斉送信機能やジョブキューへの切り替えを検討する。

### デモ用ワンクリックログイン

`DEMO_LOGIN_ENABLED=true` のとき、ログイン画面・会員登録画面に「ワンクリックでログイン」が表示される。
押すたびにお試しアカウント（メール確認済み・チケット `DEMO_LOGIN_TICKETS` 枚）が作成され、閲覧者ごとに
データが分かれる。IP ごとに 1 時間 10 回まで。本番環境（`ENV=production`）では自動的に無効になる。却下すると景品は「所持中」に戻り、再申請できる。

### ガチャを新しく公開するとき

1. 景品管理で景品を登録（画像は 5MB 以下。自動で WebP に変換・縮小・位置情報を除去）
2. ガチャ管理で「新しいガチャを作成」（下書き）
3. 「景品・確率・在庫」タブで景品を追加し、重み（確率方式）または在庫数（ボックス方式）を設定。画面上で提供割合を確認
4. ラストワン賞を設定する場合、確率方式では総口数を設定する
5. 公開ページで提供割合・残り口数の表示を確認してから「公開する」

**抽選開始後の制約**：抽選方式の変更、在庫総数の直接変更、付与済みラストワン賞の変更はできない（在庫は「在庫調整」で増減）。
重みの変更は可能だが、確率表示が変わるため告知のうえ行うこと。すべての変更は操作履歴に残る。

## チケットとポイント

- **チケット**：広告視聴・アンケート・ログインボーナス・友達紹介などで獲得し、ガチャを引くときに使う
- **ポイント**：ガチャのポイント景品（景品管理で「ポイント景品（pt）」を 0 より大きくした景品）が当たると自動で加算され、ポイント交換に使う
- 付与・調整：ユーザー管理の詳細画面から、チケットとポイントをそれぞれ付与・減算できる（操作履歴に記録）

## ポイント交換（デジコなど）の運用

1. **交換景品・ギフトコード**で景品を追加（必要ポイント・額面・在庫・1 人あたりの上限）
2. デジタルギフトは「コード登録」からギフトコードを 1 行 1 件で貼り付けて登録（暗号化して保存。重複は除外）。
   コード在庫があれば、会員の交換と同時に自動でお渡しされ、画面とメールでコードが届く
3. コード在庫がないときの申請は**ポイント交換の申請**に「受付」で残る。コードを入力して「お渡しする」か、コードを登録すると古い申請から自動でお渡しされる
4. 発送する景品は、発送後に追跡番号を入力して「発送済み」にする
5. 取消する場合は理由を入力して「取り消してポイントを返還」（会員に通知）
- コード在庫が 0 の景品は一覧で警告表示される。定期的に補充すること
- デジコの API 契約後は、自動発行（`app/services/gift_issuer.py`）を実装すると、在庫がなくても自動で発行できる

## SMS 認証

- 開始手順：Twilio の契約 → 環境変数 `SMS_BACKEND=twilio`・`TWILIO_*` を設定 → システム設定の「SMS 認証を必須にする」を有効化
- 有効にすると、未確認の会員はガチャ・チケット獲得・ポイント交換の前に電話番号の確認画面へ案内される
- 不正対策：1 つの電話番号は 1 アカウントのみ、送信回数・入力回数に上限あり

## 動画リワード広告・友達紹介

- 動画広告の案件は種類「動画リワード広告」で登録する。1 日の上限回数はシステム設定「動画リワード広告の 1 日あたりの視聴上限回数」（既定 5 回）
- 友達紹介の特典枚数はシステム設定で変更。**友達紹介**画面で紹介人数の多い会員を確認できる（不正な大量紹介の確認）

## お客さま向けのデモ用リンク

- `./scripts/demo-link.sh`：サイトを起動し、Cloudflare の一時リンクを表示する。リンクが動いていればそのまま使い、PC の再起動などで止まっていれば新しく作る（アドレスが変わるので、お客さまに新しいリンクを送る）
- `./scripts/demo-link.sh status`／`stop`／`new`（作り直し）
- 一時リンクは PC が動いている間だけ使える。常時公開するにはサーバーへの公開が必要（`deploy/README.md`）

## メール（確認メールが届かないとき）

- 開発・デモ環境の初期設定では、メールはすべて**テスト用の受信箱（Mailpit：http://localhost:8030）**に届き、実際のメールアドレスには送られない
- お客さまに実際に登録してもらうには、`backend/.env.mail.example` をコピーして `backend/.env.mail` を作り、Gmail（アプリ パスワード）などの送信設定を入れて `./scripts/demo-link.sh` を実行する
- 設定の確認：`docker compose exec backend python -m app.cli check-mail 自分のメールアドレス`（失敗した場合は原因が表示される）
- 届かないと問い合わせがあったら：迷惑メールフォルダの確認 → 管理画面のユーザー詳細で「確認メールを再送」→ ご本人と確認できれば管理者が「確認済みにする」（新規登録特典も付与される・操作履歴に記録）
- 確認メールのリンクの有効期限は 24 時間。確認済みのリンクをもう一度開くと「確認済みです」と表示される（ログインはされない）
- 本番は独自ドメインの送信サービス（SES・SendGrid・Resend など）を使い、SPF / DKIM / DMARC を設定する（Gmail からの大量送信は迷惑メール扱いになりやすい）

## 定期実行

| 頻度 | コマンド | 目的 |
|---|---|---|
| 毎日 | `python -m app.cli purge-pii` | 完了・却下・取消から保持期間（既定 90 日）を過ぎた申請の配送先を消去 |
| 毎日 | `python -m app.cli verify-draws` | 抽選結果の HMAC を照合（不一致があれば終了コード 1） |
| 毎日 | DB バックアップの成功確認 | マネージド DB の自動バックアップ |
| 毎週 | 成果通知ログで `bad_signature` / `ip_not_allowed` の急増がないか確認 | 不正な通知の検知 |

## 監視

- `GET /api/health`（DB 接続を含む）を外形監視する
- Sentry：未処理例外が送信される（個人情報は送信しない設定）
- アラートの目安：5xx の増加、`rate_limited` の急増、交換申請の滞留、流通チケット数の急増（不正付与の兆候）

## 障害対応

| 事象 | 確認・対処 |
|---|---|
| 「抽選できない」問い合わせ | ユーザー詳細の抽選履歴・チケット履歴を確認。通信断の場合でも、同じ抽選は冪等キーで 1 回だけ記録されている |
| チケットが減ったのに結果がない | `ticket_transactions` の `ref_id`（抽選 ID）から `draws` を確認。抽選と消費は同一トランザクションのため、片方だけ存在することはない |
| 成果が反映されない | 広告・アンケート管理 › 成果履歴（不承認理由）と成果通知ログ（署名不正・時刻ずれ・クリック不明）を確認。正当な成果なら管理者付与で補填 |
| メールが届かない | SMTP サービスの送信ログ・バウンス、SPF / DKIM 設定。アプリはメール送信失敗で処理を止めず、エラーを記録する |
| 不正アクセスの疑い | 該当ユーザーを停止（全セッション失効）、操作履歴・ログイン端末を確認 |
| 鍵の漏えい | `SECRET_KEY` を交換すると全セッションが無効化され、既存の抽選結果の HMAC 照合は不一致になる（交換日時を記録しておく）。成果通知の鍵は事業者と同時に交換 |

## 広告・アンケート事業者の追加

1. 事業者から、成果通知のパラメータ仕様・署名方式・送信元 IP を入手する
2. 署名方式が汎用 HMAC（[API 仕様書](api.md#成果通知ポストバックの仕様)）と同じなら、
   `backend/app/providers/registry.py` の `PROVIDERS` に `"名前": HmacProvider("名前")` を追加するだけでよい
3. 異なる場合は `BaseProvider` を継承したクラスを作成し、`parse()` で署名を検証して `PostbackData`（成果 ID・click_id・状態）を返す
4. 環境変数 `POSTBACK_SECRET_<名前>`（必要なら `POSTBACK_IPS_<名前>`）を設定
5. 事業者の管理画面に成果通知 URL `https://<公開ドメイン>/api/postbacks/<名前>` を登録
6. 管理画面で案件を作成。遷移先 URL には成果照合用の `{click_id}` を必ず含める
7. 事業者のテスト通知で、付与・重複通知・署名不正の挙動を確認する

付与は「署名が正しい」「click_id が実在し、その案件が同じ事業者のもの」「成果 ID が初回」「1 人あたりの上限内」
のすべてを満たす場合だけ行われる。成果の取消（チャージバック）通知への対応が必要な場合は、`status=rejected` を受けた際に
管理者付与で減算する運用とするか、取消処理をアダプターに追加する。

## 法令確認チェックリスト

本システムは、チケットを **無償で付与** する前提で設計しています。公開前に、サービスの実態に応じて専門家の確認を受けてください。

- [ ] **景品表示法**：景品の最高額・総額の上限（懸賞・総付景品の区分）。参考価格は景品管理で記録できる
- [ ] **資金決済法**：チケットを有償で販売する場合は前払式支払手段に該当する可能性（現状は有償販売の機能なし）
- [ ] **刑法（賭博罪）**：有償で取得したチケットで財産的価値のある景品を得る仕組みにしないこと。景品の換金・チケットの譲渡は利用規約で禁止済み
- [ ] **個人情報保護法**：利用目的の明示（プライバシーポリシー）、委託先の監督、開示等請求への対応手順
- [ ] **特定商取引法**：有償サービスを提供する場合の表示
- [ ] **広告事業者・アンケート事業者の利用規約**：インセンティブ（報酬付き）トラフィックの可否、表示上の制約
- [ ] **ガチャの表示**：提供割合・残り口数の表示（実装済み）、業界ガイドラインとの整合
- [ ] 利用規約・プライバシーポリシーの本文（`frontend/src/app/terms`・`privacy` は雛形）
