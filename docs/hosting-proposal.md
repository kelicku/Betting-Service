# サーバー構成のご提案（同時接続 1,000〜2,000 人規模）

対象：わくわくガチャ（Next.js フロントエンド／FastAPI バックエンド／PostgreSQL／Redis）
前提：初期費用を抑えつつ、ラストワン賞の終盤や SNS のイベント時のアクセス集中に耐えること。

> 料金は 2026 年 10 月時点の公開料金をもとにした**概算**です。契約前に各社の最新料金で見積もりを取り直してください。

## 1. 必要な構成要素

| 要素 | 役割 | 最小構成の目安 |
|---|---|---|
| フロントエンド | 画面の配信（Next.js） | 1〜2 台（1 vCPU・1GB） |
| バックエンド | API・抽選（FastAPI） | 2 台（各 2 vCPU・2GB、ワーカー 2〜3） |
| PostgreSQL | 会員・残高・抽選結果 | マネージド（2 vCPU・4GB、最大接続数 200 以上、自動バックアップ） |
| Redis | レート制限をサーバー間で共有 | マネージドの最小プラン |
| 画像の保存 | 景品画像など | S3 互換ストレージ＋CDN |
| メール送信 | 確認メール・ギフトコードのお知らせ | SES・SendGrid など |
| SMS 送信 | 電話番号の確認 | Twilio（1 通あたりの従量課金） |

日本の利用者向けのため、**東京リージョン**（または国内の事業者）を推奨します（シンガポールなど海外リージョンは 1 回の通信ごとに 50〜80ms ほど遅くなります）。

## 2. 構成案

### 案 A（推奨）：マネージドのコンテナサービス（東京リージョン）
Fly.io（東京）、AWS App Runner / ECS（東京）などで、フロントエンドとバックエンドのコンテナを動かし、データベースと Redis はマネージドを使う。

- 長所：サーバーの保守（OS 更新など）が不要。台数を管理画面から増減でき、アクセス集中時に一時的に増やせる
- 短所：VPS より割高
- 月額の目安：**約 1.5〜3 万円**（アクセス量・データベースの大きさによる）

### 案 B：AWS の最小構成（東京）
ECS Fargate（またはLightsail コンテナ）＋ RDS for PostgreSQL＋ElastiCache＋S3/CloudFront。

- 長所：将来の拡張（読み取り専用のデータベース追加など）がしやすい。信頼性が高い
- 短所：設定項目が多く、初期構築の手間がかかる
- 月額の目安：**約 2.5〜4.5 万円**

### 案 C：国内 VPS 1 台（ConoHa VPS・Xserver VPS など）
8GB 前後の VPS 1 台で、現在の docker compose 構成をそのまま動かす。

- 長所：最も安い
- 短所：1 台が止まるとサービス全体が止まる。バックアップ・セキュリティ更新を自分たちで行う必要がある。アクセス集中時にすぐ増強しにくい
- 月額の目安：**約 5 千〜1.5 万円**

### Vercel について
Vercel はフロントエンド（Next.js）だけを動かすサービスです。バックエンド・データベース・Redis は別のサービスに置く必要があり、フロントエンドとバックエンドの間の通信が遠回りになる場合があります。
今回の構成では、フロントエンドもバックエンドと同じ場所（案 A〜C）に置く方が、速度・費用・管理の点で有利です。

**おすすめ**：最初は案 A で公開し、利用者数と売上を見ながら、必要に応じて案 B へ移行。

## 3. 負荷試験の結果（開発用 PC での参考値）

`tools/loadtest/run.py` で、会員がログインしてガチャ一覧・詳細・残高を見ながらガチャを引く動きを再現しました。
試験環境：8 コアの PC 1 台（データベースも同じ PC）、バックエンドのワーカー 4。

| 試験 | 結果 |
|---|---|
| 同時会員 300 人（1 人が数秒ごとに操作する、実際より重い想定）・45 秒 | 約 290 件/秒、**エラー 0 件**。画面の読み込み（中央値 0.15〜0.5 秒、95% 1.1〜1.4 秒）、ガチャ（中央値 0.65 秒、95% 3 秒） |
| ラストワン競合：残り 300 口に 600 人が同時に 1 回ずつ | 9 秒で処理。成功 300 件・**ラストワン賞は 1 件だけ**・口数の超過なし・チケットの二重消費なし |

実際の会員は 1 人あたり 5〜10 秒に 1 回程度の操作が一般的なため、この結果は「普通に遊ぶ会員」換算で **約 1,000〜1,500 人の同時接続**に相当すると見込んでいます。
目標の 2,000 人に対しては、バックエンドを 2 台（合計ワーカー 4〜6）にすることで余裕を持たせる想定です。本番環境でも公開前に同じ試験を行い、確認します。

### 試験で見つかり、修正した点
- データベースの最大接続数（100）を超えてエラーになる設定 → 1 ワーカーあたりの接続数の上限を設定できるようにし、上限に達したら短時間待つようにした
- 同じガチャに抽選が集中すると、完売後の抽選も順番待ちになっていた → 完売・チケット不足はロックを待たずにすぐお断りするようにした
- ラストワン賞の付与後に在庫を追加すると、次の完売時にエラーになる → 2 回目は付与しないように修正（テストを追加）
- ガチャ一覧・詳細を 1 秒だけキャッシュし、アクセス集中時のデータベースの負荷を軽減（残り口数は最大 1 秒程度の遅れ。抽選の直後は最新）

## 4. 設定値の目安

```
WEB_CONCURRENCY=2              # バックエンド 1 台あたりのワーカー数（2 vCPU なら 2〜3）
DATABASE_POOL_SIZE=10          # 1 ワーカーあたりの DB 接続数
DATABASE_MAX_OVERFLOW=5
# 「台数 × ワーカー数 × (POOL_SIZE + MAX_OVERFLOW)」 < データベースの最大接続数 − 20（管理用の余裕）
#  例：2 台 × 2 ワーカー × 15 = 60 本 → 最大接続数 100 のデータベースで可
REDIS_URL=...                  # 2 台以上にする場合は必須（レート制限の共有）
```

ガチャの抽選は、同じガチャに対しては 1 件ずつ順番に処理します（ラストワン賞や在庫の重複を防ぐため）。
ラストワン賞の終盤など 1 つのガチャに集中した場合、1 ガチャあたり毎秒数十件の処理となり、混雑時は数秒待つことがあります（結果が二重になることはありません）。
